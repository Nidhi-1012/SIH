# NER SafeRoute / NER-LINK AI — Project Context

## What this is

AI-assisted safe-routing and logistics platform for North East India (SIH26002). Core premise: optimize routes for **safety over speed** — a P0 medical shipment should get routed away from a landslide-risk segment even if it's slower, using live rainfall + crowd-sourced hazard reports + terrain susceptibility. See `implementation_plan.md` (original 7-day sprint) and `implementation_plan_phase2.md` (role-based access + live tracking, current work) for full detail. This file is the quick-reference; those two are the source of truth for task-level plans.

## Architecture decisions (don't re-litigate these without a reason)

- **Supabase = auth/identity only. FastAPI/SQLAlchemy = the single system of record for all domain data** (segments, incidents, alerts, telemetry, drivers). Do not create a parallel `profiles`/`hazard_reports`/`driver_locations` schema in Supabase Postgres — that was an early ChatGPT-generated plan's assumption and it's a rebuild, not a fix. See `implementation_plan_phase2.md` §"Where the ChatGPT plan assumes a rebuild it doesn't need".
- **Role lives in Supabase `app_metadata`, never `user_metadata`.** `user_metadata` is client-editable and must never be trusted for authorization — that's how the current build lets anyone self-register as an officer. Role is set server-side via a backend endpoint using the Supabase **service_role key** (`.env` only, never client-side).
- **Driver location tracking reuses the existing `VehicleTelemetry` model** rather than a new `driver_locations` table — add a `drivers` table (user_id ↔ stable `DRV-00X` id) instead of altering telemetry's schema.
- **Live driver locations are visible to `officer`-role sessions only** — not other drivers, not public users. Gated via a `require_role("officer")` dependency on the officer-facing endpoint.
- **One frontend file, one source of truth.** `mobile/app.html`, `mobile/index.html`, `frontend/public/mobile/index.html` were exact-duplicate copies of `frontend/user/index.html` that drifted apart when only some were patched — collapsing this is Phase 0. If you find yourself editing more than one HTML file to ship one feature, stop and check whether a duplicate crept back in.

## Local dev backend

Docker/Postgres aren't running in this environment, so the real backend on port 8000 (which `frontend`'s Vite dev server on port 3000 proxies `/api` to) is started manually with the SQLite fallback: `DATABASE_URL="sqlite:///./dev.db" uvicorn app.main:app --port 8000` from `backend/`, using `backend/venv`. `dev.db` is gitignored (`*.db`) and persists signups/reports across restarts — it's not a throwaway. If both `localhost:3000` and this backend are up, the full signup → login → app flow actually works end-to-end (live-verified for Phase 2/3/4, see below) rather than 500ing through the proxy.

## Conventions

- Never hardcode secrets in any file the browser loads. `.env` is gitignored and confirmed untracked — keep it that way, and keep the service_role key backend-only.
- Don't add new one-off `fix_*.py` root-level patch scripts — that pattern is what caused the duplicate-file drift Phase 0 is cleaning up. Edit the source file directly.
- New DB schema needs go through new tables where possible (see Database row above) since there's no migration tool — flag it explicitly if a change genuinely requires altering an existing table's columns, since that needs more care without Alembic.
